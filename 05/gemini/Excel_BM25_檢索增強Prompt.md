## 二、檢查選用的 Excel 附件與欄位

- **第二階段只需提供這份 `.md`，學生自己的 `.xlsx` 為選用附件**，仍延續第一階段的**同一個 AI 對話**。自動檢查本輪附件、本對話先前已提供且目前可實際讀取的 Excel，以及原專案中已有的學生知識庫；不能只看檔名就假設已取得資料，也不可將 `web_cache.xlsx` 視為學生知識庫。
- **如果沒有任何可實際讀取且具檢索價值的 `.xlsx`，直接以 DDGS 為主要檢索範例**，跳過針對實際 Excel 的 schema 分析，繼續完成 Flask 專案。建立可為空的 `data/` 目錄與完整 Excel BM25 讀取、欄位辨識、索引及 Checkbox 功能，不建立虛構的學生 Excel、不猜測特定欄名、不追問或要求補傳附件。日後學生放入有效 Excel 即可自動建立索引，不需再次請 AI 修改程式。若已有可用 Excel，則納入實際檢索範例，同時保留 DDGS。
- 若有 Excel，**先實際讀取檔案，再依其內容設計 Excel 檢索功能**。逐份 Excel、逐個工作表觀察：工作表名稱、欄位名稱與順序、列數／欄數、資料型態（schema）、空值比例、常見值與類別分布（value domain）、不同文字欄位的內容長度、數值欄位的最小／最大值、日期欄位的時間範圍，以及**前 10～20 筆非空白資料**。如只有少於 10 筆，則查看全部現有資料。欄位型態不能只依欄名或前一筆推測；適度抽查後段資料，確認是否混合型態或大量空值。
- Excel 可能很大。**探索階段不需要把整份 Excel 印到對話，也不要為了顯示範例載入不必要的大量記憶體**；可使用 `openpyxl` 的 `read_only=True` 與逐列讀取、有限樣本及統計資訊來判斷欄位。依實際需求兼顧大型資料檔的記憶體消耗。**前 10～20 筆僅供觀察與判斷，不代表最後只能建立 10～20 筆索引**；正式索引仍應涵蓋選定工作表的所有有效資料列。
- **依 schema、值域與實際內容，決定每份 Excel／每個工作表可以一起檢索的文字欄位**。例如 `標題`／`title`、`內文`／`內容`／`content`／`body`、`摘要`／`summary`／`description`、`關鍵字`／`keywords`／`tags` 等有實質語意的欄位；必要時也可選擇名稱、分類或其他有意義的短文字欄位。**同一筆資料應能結合多個適合的欄位**作為 BM25 文件（保留適當欄位分隔，避免文字直接黏在一起），而不是固定只檢索標題，亦不是無條件把每個欄位全部拼入。
- URL、流水號、純數值 ID、雜湊碼、無意義代碼、純日期、Excel 列號等不要當成主要 BM25 檢索內容。可將有效 URL 留作**來源資訊**，其他欄位則按用途保留在中繼資料。欄位名相似但實際值域不同時，以**資料內容**為準；不同檔案或工作表可以有不同欄位對應，將實際使用的欄位選擇集中在易於調整的設定中。
- 若有可用 Excel，在實作前請簡要回報**各工作表的資料規模、主要欄位／值域，以及最後選用哪些檢索欄位、哪個欄位代表標題及來源網址**；不必貼出整份 Excel 或大量個人資料。沒有可用的文字欄位、檔案毀損或無法開啟時，說明具體原因、略過無效檔案或工作表，繼續使用其餘有效資料；若全部無效，直接以 DDGS 為主要檢索範例，不要求補傳 Excel，也不得假裝索引已建立。

## 三、Excel 格式與檢索資料範圍

- 在專案下建立 `data/` 放 Excel，沒有學生 Excel 時也需保留目錄（解壓縮後存在，或啟動時自動建立）。若有上傳且可安全交付的 `.xlsx`，將其原樣放進 `data/`，未來學生只需新增或更換 `data/*.xlsx` 即可；略過 Excel 暫存檔（例如 `~$...xlsx`）及保留名稱 `web_cache.xlsx`（含其暫存檔）；此網頁快取絕不可進入學生知識庫索引。可讀取每個 Excel 的所有工作表，每一筆**非空白列**作為一筆可檢索文件。
- 各 Excel 欄位名稱不保證相同，請先依上一節的 **schema、值域與前 10～20 筆資料**，選出具有檢索價值的**多個文字欄位**（例如標題＋摘要＋內文＋關鍵字）共同建立文件；若欄位名稱不典型，依內容判斷實際用途。不要把所有非空白欄位無條件拼進文件，也不要把正式索引限於範例的 10～20 筆。不同工作表可以各自設定欄位對應，避免綁死某位學生的固定 Excel 格式。
- 來源網址可能在 `網址`、`網頁`、`連結`、`來源網址`、`URL`、`url`、`link`、`source_url` 等欄位，應自動辨認，並允許在 `app.py` 上方手動指定。該欄位只用來建立出處，不要把網址當作主要關鍵字語料。空白、NaN、無效網址須安全略過。
- 每筆文件保留 `title`（若無標題則以部分內容命名）、`text`、`url`（可空）、`file`、`sheet`、`row` 等中繼資料，以便查詢結果能回到對應的 Excel 記錄。不要憑空補造來源 URL 或內容。
- **不論本輪有無 Excel 都要完成兩種檢索功能。** 有有效 Excel 時，依真實資料分析選取欄位，並將可安全交付的 `.xlsx` 放進成品 `data/`；沒有有效 Excel 時保留空的知識庫目錄，不造假學生資料。對日後新增或更換的 Excel，程式需自動依欄位名稱、實際值域及有限樣本辨識可檢索文字、標題與來源網址，允許手動覆寫設定，但不以手動改程式作為必要步驟。沒有有效資料時不得建立空 BM25 索引或沿用已失效索引；一般聊天與 DDGS 繼續可用，只有勾選 Excel 檢索才顯示「尚未找到 Excel 資料」，不要求上傳。

## 四、BM25 與中英文斷詞

- 必須使用 `rank-bm25`（例如 `rank_bm25.BM25L`，屬於 BM25 家族，適合示範資料筆數較少的情況）和 `jieba`。中文文本用 `jieba.lcut()` 斷詞；英文以規則式抽取英文單字／數字、統一小寫（`casefold`），不要只用中文 jieba，也不要將整段英文當成一個 token。
- **文件與使用者 query 一律使用同一個 tokenizer**。混合中英文字串如「臺灣 AI 模型」能同時得到中文詞與英文 `ai`、數字等 token；略過標點、空白與空字串，不要重複加入同一段英文 token。可以保留少量簡單的程式註解供學生理解。
- 用 BM25 計算 query 對文件的分數，先排序取前 `TOP_K = 3` 筆，再套用**可設定的 `MIN_BM25_SCORE` 門檻**（預設可用 `0.1` 作課堂起始值）。只有分數達標**且文件至少與 query 共用一個有效 token** 才可提供給模型；不足門檻者絕不可假稱檢索成功。
- **BM25 分數不是 0–1 的語意相似度機率**，也不代表保證正確，請在必要的 README 或設定註解中說明門檻應依資料集實測微調。空語料、空 query、只有 1–2 筆資料、沒有匹配結果時均不得拋出錯誤。
- 只用達標的前幾筆文件，且用 `MAX_CONTEXT_CHARS = 4500` 等簡單限制避免把整份 Excel 全送入模型；不必做 embeddings、重排模型或複雜 RAG framework。

- **NumPy 回傳型態防錯（實際 Windows regression）**：`BM25L.get_scores()` 回傳 NumPy `ndarray`，不能使用 `if raw_scores`、`if not raw_scores`、`raw_scores or []` 或 `max(raw_scores) if raw_scores else 0.0` 判斷是否為空；多元素陣列會觸發 `ValueError: The truth value of an array with more than one element is ambiguous. Use a.any() or a.all()`。改用 `len(raw_scores) > 0` 或 `raw_scores.size > 0`；例如 `max_score = float(max(raw_scores)) if len(raw_scores) > 0 else 0.0`。`.any()`／`.all()` 是元素內容判斷，不等於非空判斷。Excel 與網頁 BM25、排序、正規化及 Pandas 相關處理都須檢查此類錯誤；確認分數與文件數一致、分數有限，轉成 Python 原生數值後才寫 JSON／NDJSON，最高分為零時不得除以零或假造相關分數。
- **空語料防護**：空知識庫、所有文字斷詞後皆為空、空 query 或網頁全部擷取失敗時，直接回傳對應的空結果／錯誤狀態，不能呼叫 `BM25L([])` 或對空陣列取最大值。單筆、多筆、零分及完全不重疊語料均需正常處理。

## 五、索引快取與自動更新

- **執行 `python app.py` 時自動完成索引檢查**，不得另加 `python build_index.py`、`python init_db.py` 等先行步驟。Flask 啟動時檢查學生的 `data/*.xlsx`（排除網頁快取及暫存檔），有有效 Excel 且沒有可用索引時，讀 Excel、斷詞、建立 BM25 索引；若沒有任何有效資料，使用空知識庫狀態而非建立空 BM25 或載入過期索引，正常啟動 Flask，無需 Excel 即可使用 DDGS 與 Gemini；索引與文件中繼資料儲存在**本機快取**，例如沿用既有 `bm25_index.json` 或可信任的 `bm25_index.pkl`（以原專案的有效快取格式為準），`requirements.txt` 需補上 `rank-bm25`、`jieba`、`pandas`、`openpyxl`。
- **沒有改過 Excel 就直接載入既有快取，不重新讀取所有 Excel 或重做 jieba 斷詞／BM25 建立**。若 Excel 新增、刪除、內容改變、工作表改變、**選用的檢索欄位或欄位對應改變**，或 tokenizer／索引設定改變，則重建；至少在每次 Flask 啟動時檢查，最好在下一次檢索前也用便宜的檔案資訊檢查，異動才進一步核對內容雜湊。
- 快取應記錄檔案清單、修改時間／大小或 SHA-256、索引版本及必要設定。快取檔損毀時可自動安全重建；快取只可載入**這個專案自己產生且可信任**的本機檔案，不要反序列化不明來源的 pickle；也可用同樣簡單的安全格式，但必須真的避免每次重新建索引。
- 新舊索引切換應保持一致，不讓查詢同時讀到一半更新的資料；使用原有簡單的 lock 或最少量鎖定即可，不需要排程服務或資料庫。

## 六、DDGS 網路搜尋、正文擷取與快取

- 使用 `ddgs==9.16.1`（沿用參考開發規格的指定版本）、`requests`、`beautifulsoup4`，明列於 `requirements.txt`，保留原 Gemini SDK 與既有依賴版本。核對實際安裝相容性、DDGS 呼叫簽名及例外型別；若指定版本無法安裝，明示原因與最小修正建議，不可偷偷換版。DDGS 由 Flask 後端普通 Python 函式呼叫，不需要 Google Search Grounding、Gemini function calling、額外搜尋 API Key 或 Agent 框架。
- 以本輪問題呼叫 `DDGS().text()` 取得多筆候選，新聞需求可用 `news()`（依實際 SDK 支援）。整理標題、摘要、URL 並去重；搜尋摘要只用於候選篩選，必須以 `requests` 擷取真正網頁正文、清理導覽列／廣告／腳本等無關內容，再切成適當段落。無法取得有效正文的登入頁、反爬頁、PDF 或 JS 空頁應略過，不得把摘要冒稱正文；本教學版不強制增加瀏覽器自動化或 PDF 解析。
- 對有效正文段落使用第四節相同中英文 tokenizer 真正計算 BM25，搭配關鍵字覆蓋率（可選 N-gram），先在同一查詢候選集合內正規化或校準不同尺度的分數，再依相關性門檻與有效 token 交集篩選。明列計分公式及測試；不要把原始 BM25 當成百分比。相關性不等於可信度，優先採用可靠且不同來源，重複轉載不算獨立證據；不固定湊滿來源數。
- 原始查詢失敗或合格證據不足時，可有限次使用核心關鍵字、別名或具體限定詞補查。一般聊天預設使用原始 query；對「那他後來呢？」等多輪省略問題，可由近期歷史保守補足主題，但不得把整份歷史、Excel 正文、金鑰或敏感資料傳給搜尋服務；不確定時保留原問題。補查不需要額外模型呼叫，若確有必要才使用原 Gemini 模型，並明示用途。
- 將主要網路參數集中在 `app.py` 上方或單一設定區，以下為可調整的課堂起始值，不是服務保證：

| 參數 | 預設 | 用途 |
|---|---:|---|
| `WEB_CANDIDATE_LIMIT` | 20 | 每輪候選上限 |
| `WEB_MAX_SOURCES` | 8 | 最終合格網頁來源上限（可為 0） |
| `WEB_MIN_RELEVANCE` | 0.5 | 校準後的相關性門檻 |
| `WEB_MAX_SEARCH_ROUNDS` | 2 | 搜尋輪數（包含首次） |
| `WEB_MAX_SEARCH_ATTEMPTS` | 3 | 每個 query 總嘗試次數（包含首次） |
| `WEB_PAGE_TIMEOUT` | 10 秒 | 單頁網路呼叫逾時設定 |
| `WEB_DEADLINE_SECONDS` | 60 秒 | 網路檢索總時間預算，不限制 Gemini 生成 |
| `MAX_WEB_CONTEXT_CHARS` | 4500 | 網路參考資料字元上限 |
| `MAX_TOTAL_CONTEXT_CHARS` | 9000 | Excel 與網路參考資料合計上限 |

- 每個 query、每個 URL 分別處理可預期例外。`DDGSException: No results found.` 不等同確認沒有資料或配額耗盡；區分成功空結果、搜尋服務故障、正文擷取失敗、相關性不足及部分成功。暫時性錯誤有限重試（例如 1、2 秒退避加 jitter，遵守 Retry-After）；所有網路呼叫設 connect/read timeout，限制回應大小、並行數、重新導向及整體時間預算，達上限停止新請求，保留已完成資料。不得吞掉程式自身 bug 或無限等待；DDGS SDK 若無法保證硬性 deadline，須採可驗證的隔離方式或明示限制。
- 外部 URL 僅允許公開 HTTP(S)，拒絕私有／loopback／link-local／metadata IP、危險 port、含憑證 URL；每次 redirect 重新驗證，防 DNS rebinding，限制代理與實際連線目的地，不能只做初次 DNS 檢查。使用正確的 UTF-8 percent-encoding／IDNA，避免中文網址失敗或雙重編碼，保留有語意的 query 參數，遵守網站使用規範及合理速率，不繞過登入或反爬限制。
- 使用獨立 `data/web_cache.xlsx`，至少包含 `queries`、`pages`、`chunks` 三個工作表。查詢快取鍵包含規範化 query、text/news、語系、候選上限與版本；正文按正規化 URL 去重，保留標題、URL、正文段落、chunk ID、擷取時間、可確認的發布日期、ETag／Last-Modified。有效快取直接重用，搜尋列表 TTL 1 小時、一般正文 7 天、新聞正文 1 天；過期可條件式請求處理 HTTP 304。新 query 即使命中正文快取也必須重算相關性。提供可調整 `WEB_FORCE_REFRESH = False`，開啟時略過有效快取重新搜尋及擷取。
- 搜尋例外、403、429、逾時或空正文不得當成有效快取；成功空結果可明確標記並採短 TTL。更新失敗可保留先前有效正文，若採用過期資料必須標示 stale 及擷取時間，不冒稱最新。快取須有 schema 版本、鎖定、批次寫入、同目錄暫存檔與原子替換；處理 Excel 被占用、損毀、公式注入、非法 XML 字元及 32,767 字元單格限制，長正文分段保存。不得覆寫學生 Excel，快取讀寫失敗時仍可使用本輪有效資料。保留名稱 `web_cache.xlsx` 不得與學生附件衝突；若同名，安全改名學生檔並更新欄位設定、明示原因。
- DDGS 只在本輪網路 Checkbox 勾選時運作；不得於啟動、載入歷史、清除聊天或只有 Excel 勾選時偷偷連網。網頁快取與 Excel 索引的生命週期分開。

- **強制分離錯誤邊界（實際 Ollama 專案 regression，兩版本皆適用）**：曾因 DDGS、網頁 BM25 與模型生成共用外層 `try/except`，導致檢索錯誤被誤報成模型回應失敗。必須分別處理 `excel_read`／`excel_index`／`excel_rank`、`ddgs_search`、`page_fetch`／`page_parse`、`web_rank`、`cache_read`／`cache_write`、`context_build`、`model_stream`、`history_write` 等實際階段；僅模型呼叫／串流本身的錯誤才使用 Gemini 模型回應失敗訊息，歷史寫入或 NDJSON 序列化錯誤也不得冒稱模型故障。每筆查詢、每個網址及每個來源各有失敗邊界，不讓單筆外部故障破壞其他有效資料。
- **失敗降級與真正的錯誤紀錄**：可預期的檢索失敗或無命中時，保留其他已取得且合格的證據；全部無證據時以原始 query 正常聊天，明示未取得本輪外部證據。快取寫入失敗不應捨棄已取得的有效正文。程式自身 bug 不得吞掉或當成正常無結果；需記錄並按既有錯誤處理受控終止。後端使用 logging 的例外紀錄（如 `logger.exception()`）保存真正失敗階段、例外型別、完整 traceback、關聯請求 ID 及必要診斷；可預期的 HTTP 狀態也要留下階段與原因。前端僅顯示安全且具體的錯誤摘要，日誌遮罩金鑰、敏感查詢、URL token 等，不將 traceback 或機密傳到瀏覽器。禁止用通用「Gemini 回應失敗」涵蓋所有例外。

## 八、檢索來源、串流事件與歷史呈現

- 保持原本 NDJSON `chunk`、`done`、`error` 事件及逐行緩衝邏輯。新增 `retrieval_status` 事件，帶 `source_type`（`excel`／`web`）、實際狀態、候選數、合格數、快取命中數或安全錯誤摘要；同一來源狀態更新不洗版，顯示真實搜尋／擷取／篩選／Gemini 回答階段，不製造假進度。原路由維持不變，不必加入 SSE 或背景工作平台。
- 新增或擴充 `sources` 事件，例如 `{"type":"sources","items":[{"source_type":"excel","title":"文件標題","url":"https://example.org/article"},{"source_type":"web","title":"網頁標題","url":"https://example.org/page"}]}`。只列實際納入本輪模型上下文且有合法網址的來源，去除重複連結，保留兩種來源的歸屬；無網址的 Excel 內容仍可供模型參考，但不顯示空連結。網頁來源保留擷取時間及 stale 狀態（適用時）。來源列表代表提供給模型的參考資料，不保證模型每句都正確引用。
- 回答文字與來源分開，依「Excel 資料來源」及「網路搜尋來源」分組；空組不顯示。來源 URL 由後端取自 Excel 或有效網頁並驗證，不由模型編造；前端安全 DOM API 建立 `<a>`，設定 `target="_blank"`、`rel="noopener noreferrer"`，所有外部文字及模型文字使用 `textContent`，避免 HTML 注入。
- 先完整生成並成功寫入歷史，再發送最終 `retrieval_status`、`sources` 與 `done`；`done` 仍表示完整回答成功保存。來源與最終檢索狀態必須附於原本模型回答物件，重新整理可還原；舊紀錄沒有新增欄位也可讀取。送往 Gemini 時僅按原 SDK 格式轉換角色與文字，不傳來源中繼資料。
- 刪除聊天清空 `history.json` 與頁面，但不刪除學生 Excel、BM25 索引或網路快取。模型失敗或串流未完整時不保存未完成問答；前端清除暫存並重新讀取歷史，不留下假成功來源。所有自建文字檔明確使用 UTF-8，歷史及快取寫入加鎖並原子替換，避免 Windows CP950 與併發損毀問題。

### 每輪檢索狀態與來源分離（強制實作）

**AI 有回答、檢索有執行、有效證據已送入模型、有可點擊的來源網址是四件不同的事。** 不能以回答文字或 `sources` 是否為空判斷檢索成功，更不能宣稱外部資料已查證模型的每一句話。

- 每一則新完成的 AI 回答下方都要有固定的「本輪檢索狀態」，即使沒有任何網址或兩個 Checkbox 都不勾選也必須顯示。連結區塊則只有合法且實際納入上下文的來源才顯示；不得以空的來源清單取代狀態提示。
- 由後端依本輪實際執行結果建立結構化 `retrieval_status`：整體狀態（`not_used`／`success`／`partial_success`／`no_evidence`／`error`）、每個來源的 `enabled`、`status`、`stage`、`error_code`（適用時）、`candidate_count`、`fetched_count`（網路適用）、`qualified_count`、`used_count`、`link_count`、`cache_hit_count`（適用時）、安全摘要及必要的 stale 資訊。未啟用、空知識庫、搜尋成功但無結果、正文擷取失敗、低於門檻、快取故障及模型未收到任何證據要能分辨；不適用的計數不造假。`used_count` 以字元／模型 context 預算裁切與去重後真正送入模型的文件數（網路為不同來源頁面數）計算，不能使用候選數或合格數冒充；`link_count` 僅計算實際可顯示的合法 URL。
- 整體狀態以啟用的來源及最終使用證據為準：未啟用為 `not_used`；有有效證據且沒有需要揭露的檢索缺口／故障為 `success`；仍有證據但有選用來源無資料或有檢索故障為 `partial_success`；無證據且無檢索故障為 `no_evidence`；無證據且有檢索故障為 `error`。部分候選失敗可呈現明確警告與計數，不因單頁 403 就把所有合格證據丟棄。檢索狀態 `error` 與 NDJSON 終止型 `error` 事件不同：前者可以降級後正常生成回答，後者才表示本輪聊天失敗。

| 情境 | 回答下方的顯示示例（數字依實際結果） |
|---|---|
| 一般聊天 | 本輪未啟用檢索，未取得新的外部證據 |
| 檢索成功 | 已提供模型：Excel 2 筆、網路 3 個來源 |
| 部分成功 | 已提供模型：Excel 2 筆；DDGS 搜尋暫時失敗 |
| 無有效證據 | 本輪未取得符合門檻的資料，以下為模型一般回答 |
| 檢索故障 | 網頁正文擷取失敗／BM25 排序錯誤（依實際階段）；若已降級回答，標明未取得相應證據 |
| Excel 無合法網址 | 已提供模型：Excel 2 筆（無可點擊來源網址） |
| 舊歷史沒有 metadata | 此筆舊紀錄未保存檢索狀態，無法確認 |

- **NDJSON 與歷史保存**：保留 `chunk`、`done`、`error`，使用 `retrieval_status` 傳送即時進度及最終狀態，前端依來源更新既有狀態列而非不斷新增。最終狀態及 `sources` 必須與本輪實際送入模型的證據一致；完整串流成功後先將原始 query、完整回答、最終 `retrieval_status` 與 `sources` 一起寫入 `history.json`，再發送最終狀態、`sources`（可為空列表）及 `done`。只有收到 `done` 才確認本輪保存成功；若沒有 `done`、串流中斷、模型或歷史寫入失敗，清掉暫存內容並從 `/api/history` 重新同步，不顯示假成功。前端保留原有 fetch 分段緩衝、UTF-8 串流解碼及安全 DOM 渲染，不假設一次讀取就是一行 JSON。
- `retrieval_status` 與 `sources` 必須附在對應回答的歷史 metadata，刷新後直接還原相同狀態及分組連結，不重新搜尋、不重新呼叫模型；舊歷史缺欄可正常讀取，但不得猜測為「未啟用檢索」。傳入模型的歷史仍只依原 SDK 格式轉換角色與文字，不附 metadata 或先前的完整檢索增強 Prompt。清除聊天不得刪除學生 Excel、BM25 索引或網頁快取。
